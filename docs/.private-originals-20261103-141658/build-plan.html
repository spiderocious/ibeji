Ìbejì links your Laptop and your Desktop into a trusted pair on the LAN. This plan takes the PRD module by module: how each one works, what it is built on, what it looks like, and the order it all gets built in. The shape of the thing

Four processes per machine, and only one of them is allowed to talk to the other machine. Everything else is a client of the local API.

The daemon is the whole product. It holds the pinned keys, the link to the peer, the file watchers, the port scanner, the permission engine and the activity log. It starts at login and runs whether or not a window is open — closing the window must never drop the link. On macOS it is a LaunchAgent in the user's session, never a root LaunchDaemon: remote commands need the user's keychain, their GUI session and their PATH, and a system daemon gets "user interaction not allowed" from the keychain and cannot open a browser for handoff.

Everything else is a client over loopback. The Electron window, the ibeji CLI and the MCP server all speak the same local HTTP API on 127.0.0.1 with a token from the user's keychain. This is what stops the UI growing private features: if the window can do it, the CLI and an agent can do it, because there is only one implementation.

One link between machines. A single authenticated, encrypted connection carries every feature — sync, tunnels, exec, handoff, clipboard — multiplexed into streams. Mutual-key TLS over pinned Ed25519 identities, even though the bytes never leave the LAN.

Territory is surveyed — the mesh, spaces, ports, routes: contour ground, drawn connections, Spectral serif leads.

Why it matters to the build, not just the look. It is the one falsifiable rule in the system — you can hold any screen against it and get a yes or no. That is what stops an ornamental stance drifting into decoration across a hundred screens, and it is also a review checklist I can be held to.

Where it gets hard

mDNS is blocked more than you expect. Corporate and guest Wi-Fi often disable multicast between clients. Manual add by IP is therefore a first-class path, not a fallback — and the empty state on the discovery list has to say "multicast may be blocked on this network; add Desktop by IP" rather than just sitting empty.
The IP changes under you. DHCP renews, Wi-Fi flips to Ethernet, the machine sleeps. Identity is the pinned key, never the address: the device row shows the current IP as information, and the link re-resolves through mDNS or the last known address on every reconnect.
A reinstall looks exactly like an impersonation. Same name, same IP, new key. The product cannot tell these apart, so it must not guess — it hard-fails and shows both fingerprints side by side with typed confirmation. Annoying on a genuine reinstall, correct every other time.
M6a

The API skeleton

Large

The local HTTP API, plus reads and exec against the peer with no permission layer yet. This is the walking skeleton: the first build where ibeji run desktop -- echo hi prints hi.

Why this is second and not fourth. The PRD groups M1 + M2 + M6 + M4 as the first milestone, and that grouping is right. The order inside it cannot be M2 before M6, because the permission engine is a thing that interposes on calls — build it first and it guards nothing, and the prompt copy gets written against a hypothetical caller instead of a real one. So: get reads and exec working end to end in Bypass only, then put the permission layer in front of calls that already work.

M2

Permissions & remembered rules

Large

Two modes per direction, a prompt that names the asker and the exact effect, and the rule that makes Prompt mode livable: always allow this exact command in this directory from this device.

The thing this module is really for. Bypass is right between two machines you own and sit at. Prompt is right for a corporate-managed machine. Neither is usable for agent work on its own: Bypass gives an agent your whole machine, and Prompt asks you to approve every git push forever. Remembered rules are the third answer — approve git push in this one repo from this one device, once, and it never asks again while everything else still asks.

What gets built

PieceKindDetail
Mode, per directionnewSet on the receiving device, changeable any time. Desktop can be Bypass toward Laptop while Laptop stays Prompt toward Desktop. Not a symmetric setting.
The permission enginenewOne chokepoint every side-effecting call passes through, whatever its origin — app, CLI, API or MCP. If it is possible to reach a side effect without passing here, that is a bug of the highest severity in this product.

Where it gets hard

"Exact command" is less exact than it sounds. git push and git push and git push origin main are three different strings. v1 normalises whitespace and nothing else — no flag reordering, no path canonicalisation beyond resolving the cwd. A rule that does not match simply prompts, which is the safe failure. Documented in the rules list so a rule that never fires is explicable.
The prompt has to reach you. If the window is closed, the daemon still receives the call — so the prompt arrives as a notification that opens the window, and the tray icon changes. A prompt nobody can see expires in 60 seconds and makes the product look broken.
Provenance must be unforgeable on the local side. The MCP server stamps provenance: mcp, but it is just an API client — a script could claim the same. v1 accepts this: provenance is for your own legibility in the log, not a security boundary. Worth saying plainly rather than implying the violet badge is a guarantee.
M4

Shared spaces

Extra large

A named folder that exists in full on both machines. One master, one replica, master wins collisions, and the replica's version is always kept. This is the module that makes "edit here, run there" feel like one computer.

Not a network mount. The replica holds real files on real disk — so your editor, your language server and your file watcher all behave normally, and the folder works when the peer is asleep. The cost is convergence: two real copies can diverge, which is why the conflict rule is decided up front rather than discovered.

Master-wins is not a cop-out, it is the correct outcome for the main use case. The master is the machine that owns the git credentials and the corporate access. A git pull on the master should beat an unsynced local edit on the replica — and the replica's edit is never lost, it is preserved beside it and surfaced.

Where it gets hard

This is the module that can lose your work. Everything else in Ìbejì is additive — a failed tunnel or a declined command costs you nothing. A sync bug overwrites files. So: atomic renames everywhere, never delete without a conflict copy, and a dry-run mode during development that logs what it would do without touching disk. I would rather ship this module late than ship it fast.
Ignore patterns are load-bearing for performance, not just tidiness. A repo with node_modules unignored is 40,000 files and a watcher storm. The defaults are pre-filled for that reason, and the space creation screen shows the file count before you commit.
Deletes are the ambiguous case. A file gone on the replica is either "I deleted it" or "it never arrived". v1 treats a replica-side delete as a change to push, and a master-side delete as authoritative — with deletes listed in the feed so a surprising one is visible. Tombstones with timestamps, not absence-as-signal.
M6b

Barrier, processes, saved commands, MCP

Extra large

The rest of the programmable surface: the sync barrier that removes the edit-here-run-there race, long-lived processes you can kill from the other machine, and the MCP server that hands all of it to an agent.

The sync barrier — the best idea in the PRD

The race it removes. You save a file on Laptop. A quarter-second later your agent runs git commit on Desktop. The save has not landed yet, so the commit captures a half-synced tree — and it is intermittent, which is the worst kind of bug to find in your own commits weeks later.

--after-sync <space> blocks until that space reports in-sync, then runs. It is a flag on the API, the CLI and the MCP tool, and it is the blessed way to sequence the product's core pattern. The barrier has its own timeout, and a space that cannot converge — peer asleep, conflict pending — fails the call with the reason rather than hanging.

Why it belongs here and not in M4. It needs M4's state machine to be trustworthy. Building it earlier would mean building it against a sync engine whose in-sync was still a guess.

M5

Port Lens

Medium

One list of every listening port across both machines, each a click from being local. This is the surface people will describe when they describe the product.

What makes it feel like magic. A dev server bound to 127.0.0.1:3000 on Desktop is, by design, unreachable from Laptop — that is what loopback means. Port Lens makes it reachable without changing the bind address, touching the firewall, or typing an IP: Laptop's daemon listens on localhost:3000 and forwards over the LAN to Desktop's daemon, which connects to its own loopback internally. From Laptop's point of view, Desktop's dev server is local.

Why tunnels never prompt. Opening a tunnel is a read, not a side effect — the remote user already exposed the mesh by pairing. But it is logged, with the connecting process name where knowable, because the log is the accountability story on a managed machine.

M3

File drop & clipboard

Small

Send a file across without a cloud round trip, and optionally let one clipboard serve both machines. The small module that gets used constantly.

File drop is deliberately dumb. Files and folders — folders as archives — land in a known inbox, default ~/Ibeji/Inbox, with a notification carrying reveal in folder. No chat, no history, no previews; those were cut to v2 and the scratchpad covers "leave a note".

No store-and-forward. If the peer is offline the send fails visibly. This is a LAN product: a queue that silently holds your file until tomorrow is worse than an error today, because you act on the belief it arrived.

Clipboard sync is off by default and visibly indicated while on. Text and images, propagating within a second. Clipboard contents are never written to any log or history — not the activity log, not a debug file. The one piece of state in this product that is deliberately unobservable.

Why clipboard sync defaults to off. A shared clipboard carries passwords, tokens and whatever you last copied out of a password manager. Having it on by default would mean every copy on a corporate machine crosses to an unmanaged one without you deciding. On, with an indicator, when you want it.

M7

Handoff

Small

Send a URL to the other machine's browser, launch an app there, and mirror Ìbejì's own notifications across. The module that quietly solves the SSO problem.

Browser handoff is the escape hatch that matters. When a SAML or SSO session lapses on the machine that owns it, you hand the sign-in URL across and click through there — on the machine whose browser profile, VPN and posture the identity provider already trusts. That is the whole fix, and it is three lines of code sitting on top of M1 and M2.

App launch opens an application on the peer, optionally with a file or folder argument — "open VS Code on Desktop at the medcord space folder". Because sync makes the folder equivalent on both machines, pointing an editor at it there is the same as pointing it here.

Handoff, not teleport. Moving a running app between machines is defined as relaunching the same app on the target, pointed at the same context. No live window migration in v1, and the word "handoff" is chosen to promise exactly that much.

Notifications mirror Ìbejì's own events — sync conflict, command finished, incoming prompt, inbox arrival — as toasts on the peer, with a per-pair toggle. Mirroring other apps' notifications is deferred: on macOS it is a permissions tar pit that would dominate the module.

M9

Trace, help & doctor

Medium · spread across the build

The module that exists because the first user of this product's API is an agent — and an agent cannot read a README, ask a colleague, or notice that the daemon is not running.

Why this is a module and not a flag. Everything else in Ìbejì is built for you. This one is built for whatever is driving the API at 2am: Claude Code, a script, you in six months. Three capabilities, each answering a question an agent otherwise cannot answer for itself — what just happened, how do I call this, and why is nothing working.

It is not scheduled as one block. doctor lands in milestone 1 while the install path is still new, the trace lands with the API in milestone 2 rather than after it, and help --json lands with the MCP server in milestone 3, generated from the same source as the tool descriptions. Retrofitting tracing onto calls that already exist means missing the ones you forget.

The trace — what happened, with the payload

Every API call, link event and permission decision, recorded with event type, timestamp, originating device, provenance, request payload, result or error, duration and verdict. Held in a capped ring buffer — 50 MB or 7 days by default, oldest dropping first — in the daemon's SQLite. Queryable from ibeji trace and from a Trace pane in the app, with the same filters in both.

Readable across the link. It is a read, so it never prompts, and that is the entire point: an agent on Laptop debugging why its own call failed needs to see Desktop's side of that call. One machine's trace tells half a story.

How it differs from the activity log. The activity log (M2) is the human, permission-focused view — what was asked, by whom, and what you decided. The trace is the diagnostic superset: it holds payloads, timings and the calls that never reached a permission decision at all. Same events, different question.

Two absolute exclusions. Clipboard contents are never traced — not in any mode, not with verbose on. A file write's payload is traced as path plus byte count, never the file body. A trace that quietly accumulates the contents of everything you synced would be the single worst artefact this product could leave on disk.
laptop ~ % ibeji trace --follow --device desktop 14:24:02.118 exec.request desktop mcp cwd ~/projects/medcord cmd git push origin feature/sync-barrier after_sync medcord 14:24:02.119 sync.barrier.wait medcord syncing 14:24:02.934 sync.barrier.ok medcord in-sync 815ms 3 files 14:24:02.936 perm.check desktop rule-matched rule git push · ~/projects/medcord · laptop 14:24:03.002 exec.start desktop pid 51204 zsh -lc 14:24:05.771 exec.exit desktop 0 2.77s stdout 142 bytes 14:24:05.773 link.stream.close desktop ok # and when it goes wrong, the reason is in the trace laptop ~ % ibeji trace --since 10m --errors 14:19:41.008 exec.request desktop mcp cmd npm run deploy 14:20:41.009 perm.expired desktop 60s error timed_out awaiting approval on Desktop hint Desktop's window was closed; the prompt was never seen

ibeji trace — pure record register, which is what a trace should be: ruled, mono, timestamped, no ornament anywhere near it. Provenance renders violet even in the terminal. The hint line is the part worth building carefully — an error that names the likely cause saves an agent a round of guessing.

Help, written for an agent

ibeji help --json emits the whole surface as one machine-readable document: every command and endpoint with its parameters, types, defaults, an example request payload, an example success response, and the complete set of error codes it can return — declined, timed_out, the barrier failures, the transport failures. An agent that has never seen Ìbejì onboards from one call instead of guessing at payload shapes and learning the error codes by hitting them.

One source, three consumers. The same definition generates the JSON document, the MCP tool descriptions and the human --help text. That is the only way they stay in agreement; hand-written tool descriptions drift from the API within two weeks, and a drifted tool description is worse than a missing one because the agent trusts it.

laptop ~ % ibeji help --json | jq '.commands.run' { "summary": "Run a command on a paired device", "endpoint": "POST /v1/exec", "params": { "device": { "type": "string", "required": true }, "cmd": { "type": "string", "required": true }, "cwd": { "type": "path", "default": "~" }, "after_sync": { "type": "string", "default": null, "note": "block until this space is in-sync" }, "detach": { "type": "bool", "default": false }, "timeout_s": { "type": "int", "default": 300 } }, "returns": { "exit_code": "int", "stdout": "stream", "stderr": "stream", "duration_ms": "int" }, "errors": [ "declined", // the user said no "timed_out", // 60s, nobody answered "sync_conflict", // barrier cannot converge "peer_offline", // not on the LAN right now "exec_timeout" // the command itself overran ], "notes": [ "runs in zsh -lc as the logged-in user", "obeys the device's permission mode" ] }

Stack & how everything is checked

Settled, with the reasoning kept on the record because this was the decision most expensive to reverse.

The stack

PartChoice
DaemonGo — one static binary, no runtime to install, good mDNS/TLS/FSEvents libraries, trivial cross-compile for the Windows and Linux degradation the PRD asks for
CLIGo, same binary with a different entrypoint. A CLI that starts in 8ms is a CLI you use in scripts
MCP serverGo, same binary, stdio mode. One artefact to install, version-locked to the daemon by construction
AppElectron + TypeScript, no framework beyond what the design system needs — it renders API state and sends intents, which is not a job that needs a state library
StylingThe design system's own CSS, used directly. _foundation.css and _components.css are already the single definition; re-expressing them in a CSS-in-JS layer would fork the source of truth
StorageSQLite per daemon for rules, log, spaces, pins, process history and the trace ring buffer. Keys in the keychain, never in the database
RepoOne repo for all four artefacts, so the app and the API it consumes are versioned together
The alternative, for the record. TypeScript end to end would have been one language and one you already know. It was declined for three reasons that all bite later rather than sooner: a Node runtime inside the LaunchAgent, a CLI slow enough to notice in scripts, and weaker native file-watching in the one module that can lose work.

How it gets checked

  • Two-daemon harness. Every test spins up two daemons in one process with an in-memory link, so pairing, permissions, sync and exec are all testable without two physical machines. This is the single highest-leverage thing to build early — without it, every bug costs a walk across the room.
  • Sync torture tests. Both sides edit, one deletes, one renames, peer offline for a day, clock skew, a 2GB file interrupted mid-transfer, a watcher storm from npm install. The module that can lose your work gets the test suite that assumes it will.
  • Permission matrix tests. Every row of the PRD's permission table, in both modes, times rule-match and no-match, times accept, decline and expiry. Including the one that matters most: no path reaches a side effect without the chokepoint, asserted by construction rather than by review.
  • Real-machine smoke. Before any milestone is called done: your actual Laptop and Desktop, on your actual Wi-Fi, through a sleep/wake cycle and an IP change.
  • Screenshots against the specimens. Each surface photographed and held against its gallery file, and against the law — is every block territory or record, and is it in the right register. A screen that cannot be classified is a screen that drifted.
  • Daemon idle cost measured, not assumed. The PRD says idle CPU near zero. That gets a number on it: CPU and memory sampled over an hour of idle with four spaces and a port scanner running, and it is a release gate, not a nice-to-have. The trace ring buffer is included in that measurement — tracing every call must not be what makes the daemon heavy.
  • The agent surface is tested by an agent. ibeji help --json is only useful if it is sufficient, so the test is: a fresh agent session given nothing but that document and a paired machine, asked to run a command on the far side. If it needs a hint from me, the document is incomplete.

Pushback & open questions

Where I think this plan is most likely to be wrong, said plainly. The five open questions from the first draft are answered and folded in; what is left is risk, and two things I would still like your instinct on.

Where I expect trouble

Sync is the module that can lose your work. Every other feature fails harmlessly — a declined command or a dropped tunnel costs you nothing. A sync bug overwrites a file. That is why it gets the longest schedule, a dry-run mode during development, and tests that assume it will go wrong. If anything in this plan slips, let it be this, and let it slip by weeks rather than being rushed.
Port Lens is the demo, and it is nearly last. That will feel wrong — it is the surface that makes people understand the product. But it depends on the link, the log and the stale discipline, and building it early would mean building those three things badly in service of a screenshot. Since all four milestones are in scope, nothing is lost by its position; it just means the thing you will want to show someone arrives late. If that bothers you, the honest trade is to move it ahead of M4 and accept that milestone 3 slips.
The daemon must stay invisible. "Idle CPU near zero" is easy to say and easy to lose: a port scanner polling every second and watchers on four unignored repos will show up in Activity Monitor, and the moment it does, you will quit it. Hence a measured release gate rather than a good intention.
60 seconds may be wrong in both directions. Too short for a build you are waiting to approve, too long for an agent that should fail fast. My instinct is that the real answer is detach long work rather than lengthen the timeout — but I would rather find that out at milestone 2 with you using it than argue it now. The trace will tell us: a run of perm.expired events is the evidence either way.
Nine modules is a long build, and the trace is what keeps it honest. The risk in a build this size is not any single module — it is me reporting a milestone done when it works on the happy path. Tracing from the first call, doctor in week one, and real-machine smoke as a gate on every milestone are the three things that make "done" checkable by you rather than claimed by me.
